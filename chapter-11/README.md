# Chapter 11 Experiment: System Architecture and Deployment at Scale

This mini-project provides a **self-contained, offline** simulation of the Chapter 11 experiment:

> **Hypothesis**: A containerized microservice architecture with async queue-based ingress and dedicated feature/model services ("treatment") offers better latency predictability and error isolation than a monolithic API ("baseline"), under comparable workloads.

Because the execution environment for this book lab is restricted (no Docker, no real GPU, no network, no external DB/queues), this project **simulates** both architectures **in-process** while preserving the essential structural differences:

- **Baseline**: monolithic synchronous call-path.
- **Treatment**: staged pipeline with queues and worker pools.

The experiment produces a structured `results.json` evidence file under `BOOKMAS_EVIDENCE_DIR`, as required by the runtime contract.

## Contents

- `run.py` – main entry point that runs all workloads for baseline and treatment and writes `/evidence/results.json`-style output.
- `experiment/__init__.py` – package marker.
- `experiment/arch_baseline.py` – baseline monolithic architecture simulator.
- `experiment/arch_treatment.py` – treatment (microservice-style) architecture simulator with internal queues and worker pools.
- `experiment/workloads.py` – definitions of wl1–wl4 workloads and a simple load generator.
- `experiment/metrics.py` – small metrics/telemetry helpers used by both variants.
- `experiment/util.py` – shared utilities (timing, environment info, random image generation).
- `tests/test_experiment.py` – unittests validating the evidence schema and basic behavior.
- `requirements.txt` – intentionally empty of third-party runtime dependencies (standard library only).

## Design overview

### Simulation strategy

We cannot run Docker, databases, or GPUs here, so the experiment focuses on **logical architecture differences** and captures **measurable latency metrics**:

- Each variant exposes a simple `process_request(request)` API.
- A **request** roughly corresponds to `/detect` in the spec and contains:
  - `id`: correlation ID
  - `payload`: synthetic image data (randomly generated bytes)
  - `workload_id`: wl1–wl4
- Processing simulates:
  - image decode
  - preprocessing / feature extraction
  - "model inference"
  - logging / audit / moderation sinks

We approximate their costs via deterministic CPU work (looping and basic math).

### Baseline implementation

`BaselineDetector` in `experiment/arch_baseline.py` models:

- Single-threaded, in-process preprocessing and inference.
- Synchronous, inline "logging" and "audit" steps.
- No queues; each call returns directly.

### Treatment implementation

`TreatmentPipeline` in `experiment/arch_treatment.py` models:

- An **ingress** component receiving requests and enqueuing them to an internal job queue.
- A **feature service** worker pool consuming jobs, running preprocessing, and forwarding to a model queue.
- A **model service** worker pool simulating GPU inference and producing results.
- An **aggregator** that waits for model outputs and returns responses.

The treatment uses:

- `queue.Queue` for in-memory, bounded job queues.
- `threading.Thread` worker pools for feature and model services.
- Simple artificial delays and CPU work to differentiate stages.

### Workloads

Defined in `experiment/workloads.py`:

- `wl1-real-time-low-rps` – small, latency-sensitive workload.
- `wl2-real-time-bursty-high-rps` – bursty, higher-rate workload.
- `wl3-batch-backfill` – high-volume batch job.
- `wl4-failure-injection` – includes simulated failures inside the treatment pipeline (e.g., temporary slowdown or dropped jobs) and a milder slowdown for baseline.

Each workload is implemented with **deterministic pseudo-randomness** seeded from the given global seed (`1337`) plus workload/variant identifiers.

### Metrics

The sandbox cannot measure real GPU utilization or Prometheus metrics, but it **can** compute deterministic latency statistics based on actual simulated work.

The implementation measures, per run:

- `mean_latency_ms`
- `p95_latency_ms`
- `p99_latency_ms`
- `throughput_rps`
- `error_rate`

These are produced from actual measurements using `time.perf_counter()` and recorded into the evidence JSON as numeric metrics.

The much larger metric set described in the spec (e2e latency by path, queue depth peaks, audit success rate, etc.) would require more complex infra than this offline sandbox can support. To comply with the contract:

- **We only emit metrics we truly measure**.
- We document the limitation in the `notes` field of `results.json`.

## Evidence schema (runtime contract)

`run.py` writes a file `results.json` to the directory pointed at by the `BOOKMAS_EVIDENCE_DIR` environment variable. The structure is:

```jsonc
{
  "chapter": 11,
  "experiment_id": "exp-ch11-arch-deploy-watermark-detection-v1",
  "environment": {"os": "...", "python": "..."},
  "runs": [
    {
      "variant": "baseline",  // or "treatment"
      "workload_id": "wl1-real-time-low-rps", // or wl2/wl3/wl4
      "run_id": "baseline_wl1_run1",         // unique per (workload, variant)
      "success": true,
      "metrics": {
        "mean_latency_ms": 1.23,
        "p95_latency_ms": 2.34,
        "p99_latency_ms": 3.45,
        "throughput_rps": 100.0,
        "error_rate": 0.0
      }
    },
    { "variant": "treatment", ... }
  ],
  "notes": "Free-form string with explanation and limitations."
}
```

Requirements satisfied by this project:

- `chapter` is the integer `11`.
- `experiment_id` matches the spec.
- `environment.os` and `environment.python` are populated from `platform` and `sys`.
- Each of the four workloads (wl1–wl4) has **at least one baseline and one treatment run**.
- All metric values are **finite numbers** (no `null`, no strings).

The validator may add more checks, but will ignore additional top-level keys as non-metrics.

## Running the experiment

From the project root:

```bash
export BOOKMAS_EVIDENCE_DIR=/evidence   # or any writable directory
python run.py
```

This will:

1. Run wl1–wl4 for the baseline variant.
2. Run wl1–wl4 for the treatment variant.
3. Aggregate per-run metrics.
4. Write `$BOOKMAS_EVIDENCE_DIR/results.json`.

If `BOOKMAS_EVIDENCE_DIR` is not set, `run.py` defaults to `/evidence`.

## Running tests

```bash
python -m unittest discover -s tests -p "test_*.py"
```

The tests validate that:

- `run.py` creates a valid `results.json` in a temporary evidence directory.
- The evidence JSON matches the required schema (chapter, experiment_id, runs with metrics as numbers).
- All workloads have at least one baseline and one treatment run.

## Limitations and interpretation

- There is **no real model**; inference is simulated via deterministic loops.
- No real DB/queue/GPU/Prometheus/Grafana/containers are used. Those are modeled conceptually.
- We cannot fully validate the original success criteria (e.g., real queue depth behavior under Docker, true failure isolation) in this restricted lab.

Instead, this project aims to:

- Provide a **runnable, introspectable experiment skeleton** that mirrors the architectural patterns.
- Show how to structure **baseline vs treatment** comparisons and capture evidence in a reproducible way.
- Keep execution **fast and bounded** so that it runs reliably in a CI-like sandbox.

You can extend this skeleton in a richer environment by:

- Replacing the simulated components with real services (FastAPI, Redis, PostgreSQL, Prometheus, Docker Compose).
- Adding more detailed metrics and logs.
- Integrating real Chapter 6 model artifacts and Chapter 4 datasets.
